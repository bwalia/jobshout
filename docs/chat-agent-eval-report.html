JobShout · Evaluation Report

Chat Agent Audit

The rebuilt chat agent ships 74 platform tools, a guard chain, an envelope contract and a full web UI. On this deployment none of it can run: the configured LLM client cannot make tool calls, so the agent invents tool results instead of making them.

2026-08-24branch feat/chat-agent-upgradeAPI :8181 · UI :3001 model qwen3-coder:30b via ollama15 live probes · 2 surfaces
Verdict — Not shippable

No, it cannot control the platform, and today it is less safe than the version it replaced. Across 15 live probes spanning agents, tasks, workflows, insight, permissions and robustness, zero tool calls executed and zero entities were returned. Thirteen of the fifteen replies contained a fabricated tool result: invented tool names, invented agents, invented task IDs, and "status": "success" for work that never happened.

The cause is a single wiring defect, not 74 broken tools. The tool layer's own unit tests pass. Fix the one defect and most of this report should be re-run from scratch — the matrix below measures a blocked system, not a bad tool layer.

02

Root cause

The chat agent sends tool definitions to a client that cannot receive them, then treats the resulting empty tool-call list as “the model has finished answering.” The model, having been told in its system prompt that tool results arrive wrapped in BEGIN_UNTRUSTED_TOOL_RESULT delimiters, simply autocompletes that shape.

Three facts combine, each harmless alone:

  • OllamaClient.SupportsTools() hard-returns false, and the client has no tools support at all — the word tools appears nowhere in its request struct. (llm/ollama.go:112–114)
  • chatagent sends ToolDefs unconditionally and exits the loop the moment ToolCalls is empty. There is no SupportsTools() check and no ReAct fallback. (chatagent/agent.go:262–283)
  • The system prompt describes the untrusted-result delimiters, giving the model an exact template to imitate. (chatagent/prompt.go:20)

The executor already solved this. executor.go:235 guards with clientSupportsTools(client) and falls back to reactLoop when the client can't do native tools. The new chat agent was written without that branch.

05

What this audit could not measure

Stating this plainly matters, because the code below the defect may well be good and this report gives it no credit either way:

  • All 74 tools. None executed once. Their correctness, org-scoping and output quality are untested end to end. Unit tests for platformtools and chatagent pass, so the logic is plausibly sound.
  • The guard chain — RBAC, policy, confirmation tokens. Never reached, since it only runs on a real tool call.
  • Memory (M1–M13). Untestable as specified: entity state, pending actions and long-term recall are all written from tool results that never occur. Conversational prose does carry context, which suggests the transcript window works.
  • Response quality rubric. Cannot be scored on fabricated content. Note the sanitiser is active — it strips URLs, UUIDs and Go errors — it simply has no rule for the fabricated tool-result block.
  • Rich UI cards, tool chips, confirmation buttons. Built and shipped in components/chat/, but never rendered, because they key off actions[] and entities[], which are always null.
06

Findings

Critical · Blocks everything

No tool-capability guard and no fallback in the chat loop

The chat agent assumes native tool-calling. With LLM_PROVIDER=ollama — this deployment's configuration — all 74 tools are silently disabled and every action becomes a hallucination. chatagent/agent.go:262–283, llm/ollama.go:112.

Critical · Data integrity

The agent reports success for writes it never performed

Probe T2 returned "status": "success" with a task ID for a task that does not exist. A user acting on that reply believes work is tracked when nothing was created. This is the exact failure class the upgrade was meant to make structurally impossible — and the looksAffirmativeSuccess guard in the loop does not catch it, because no action ever registered as failed.

Critical · Trust

Fabricated entities are presented as real records

Invented agents (“Security Analyst”, “Compliance Officer”), invented task IDs (task-104) and invented workflows (“Incident Response”) are returned as system data with stable-looking IDs. Nothing in the reply marks them as unverified.

High · Output leak

Internal prompt scaffolding renders to end users

BEGIN_UNTRUSTED_TOOL_RESULT / END_UNTRUSTED_TOOL_RESULT appear verbatim in the chat bubble on web and in API responses. SanitiseMessage has no rule for these delimiters. Your own prior session — the article-scheduler conversation still in the dock — shows the same leak in real use.

High · Safety gate never armed

“Delete the DevOps agent” produced no confirmation

The two-phase confirmation flow exists in chatagent/confirm.go but is unreachable, because it triggers on a destructive tool call. Today the request is answered with an invented agent list. The gate is untested in production conditions and must not be assumed working.

Medium · Ambiguity handling

The Data / Database trap was not disambiguated

With two similarly named agents present, “run Data” neither asked nor matched. Whether the underlying ByName matcher handles this correctly is untested end to end — its unit tests pass.

Medium · UI defect

The chat dock renders on top of the full chat page

At /chat both surfaces mount simultaneously — the dock overlays the page's own message list and session sidebar, producing two stacked chat UIs. The dock should suppress itself on that route.

Low · Streaming fidelity

SSE emits one token event containing the entire message

The transport is correct and done carries the full envelope, but there is no incremental delta, so the streaming UI cannot show progressive text. Separately, POST /chat/route still returns a vestigial intent field — it reported intent:"help", confidence:1 on an agent-list reply.

07

What to do, in order

1

Never send tool definitions to a client that cannot use them

Guard the loop with SupportsTools(), exactly as executor.go:235 does. When the client can't do native tools, either fall back to the existing ReAct loop or fail loudly at startup. Silently degrading to a hallucination machine is the worst available option.

unblocks every capability ID in the matrix
2

Give the Ollama client real tool-calling

Ollama's /api/chat accepts a tools parameter and qwen3-coder:30b supports it — the model registry already tracks a per-model CapTools flag that the client-level false overrides. Wire the request field and derive SupportsTools() from the model's capability instead of hard-coding it.

the actual fix for this deployment
3

Make “claimed but not done” impossible, not merely discouraged

If the reply asserts an action and actions[] is empty, the message is wrong by construction — refuse to send it. Add a startup assertion too: if no tool call has ever succeeded in a session where the model claimed one, that is a system fault, not a bad answer.

the critical data-integrity finding
4

Strip prompt scaffolding in the sanitiser

Add the untrusted-result delimiters and bare tool-call JSON to SanitiseMessage. Cheap, independent of the above, and stops the most visible symptom immediately.

the output-leak finding
5

Re-run this evaluation from scratch

Everything in sections 04 and 05 measures a blocked system. Once tools execute, the 74-tool surface, the guard chain, memory and the UI cards all need their first real assessment — none has been exercised once.

restores confidence in the other ~90% of the work
6

Suppress the dock on /chat, and emit real token deltas

Two contained UI fixes, independent of the backend work.
